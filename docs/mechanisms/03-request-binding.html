The Call That Came Back Changed

A user approves one specific action, in one specific conversation, at one specific moment. A binding writes down all three. When the same call reappears with any of them changed, it is no longer the call that was approved.

What a binding is not

It is an intra-process consistency check, not a cryptographic one. A Binding is created and verified inside the same trusted application process, and it is not designed to cross a trust boundary. Nothing in it is keyed, so it detects modification, not forgery by something that can construct bindings of its own.

It also detects change rather than reuse, which is the sharper limit and the one this strip does not otherwise show. verify_binding is a pure function that keeps no record of what it has already accepted. The same binding, with the same arguments and the same message hash, verifies every time it is asked for as long as its TTL lasts. Every refusal drawn above came from something differing: a changed recipient, an advanced conversation, an expired window. An exact replay inside the window differs in nothing, and passes. Consuming a binding on first use would take state this function does not keep.

If bindings ever had to travel between processes, this would need to become a keyed HMAC over the tool, argument hash, message hash, creation time and TTL, checked against a server-held secret. That is written down as future work rather than quietly implied by the word “binding”.

Mechanism only. bind_request, verify_binding, args_hash, message_hash and ttl are real. The addresses are invented. No benchmark numbers appear, because numbers go stale and mechanisms do not. Verified against Vörður 2.0.0, commit a0e51be. API names, policy fields and orderings can change too, not only numbers.
