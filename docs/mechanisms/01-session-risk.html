The loop runs backwards too

The same memory works in the other direction, and there is no confidence threshold to tune. Two outbound results write escalated=True: a remembered canary, and a DLP hard block. A provenance refusal or a rate-limit refusal refuses without writing it. escalated_tool_policy ships as require_auth, so a later call is refused unless something authorizes it. A leak that was caught once makes the next request harder, not easier. Strip 02 draws this from the other end.

Mechanism only. Every name on these panels is a real setting or call in the library: process_inbound, check_tool_call, contaminated_tool_policy. No benchmark numbers appear here on purpose, because numbers go stale and mechanisms do not. Panel 05 was measured both ways, at the default policy and hardened. Verified against Vörður 2.0.0, commit a0e51be. API names, policy fields and orderings can change too, not only numbers.
