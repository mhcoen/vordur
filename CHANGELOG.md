# Changelog

All notable changes to Vörður are documented in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed
- **Existing positional security contexts silently lost their sensitivity.** The new `principal_id` field is now keyword-only, preserving every pre-existing `SecurityContext` argument position. Regression tests verify that a positional sensitive context still tokenizes inbound PII and blocks sensitive egress after contamination.
- **Existing positional policies silently lost their capability scopes.** The new `destructive_tools` field is now keyword-only, so a positional scope dictionary remains an allowlist rather than becoming a destructive-tool declaration. Empty scopes still deny all tools.
- **Custom destructive tools skipped automatic confirmation.** Authorization and `auto_confirm_destructive` now share the same classification, including explicit empty/replacement sets. Regression tests cover absent, denying, and approving confirmation handlers in both client and server mode.
- **ROC/PR development-cap pruning split global duplicate-text clusters.** Pruning now retains each original cluster and its first-record stratum instead of separating members by suite or label. The real corpus leaked a duplicate across development and test at caps of 100 and 10; both now remain disjoint. Capped split membership can change, so operating points must be recomputed when using the corrected splitter; frozen published artifacts are not regenerated by this fix.

## [3.0.0] - 2026-09-05

This release renames the project and its package: GuardLLM is now Vörður, installed as `vordur` and imported as `import vordur`. The rename is the reason for the major version, and two smaller contract changes ride with it: a missing confirmation handler now reports as a configuration failure with a new reason string, and `SecurityContext.mode` now rejects anything other than `"client"` or `"server"`. It also carries everything that landed after 2.0.0: the privacy vault and its persistence, the gateway, in-process Rego policy, YAML policy files, the support bundle, the inbound and provenance bounds, and the fixes below.

### Added
- **A no-copy exemption for the principal an egress is addressed to**, contributed in #39. The no-copy rule protects untrusted content from reaching a *third* party, but it compared an egress against every untrusted span including ones the recipient authored, so returning someone their own words read as exfiltration. `check_outbound(egress_to_principal_id=...)` now skips the untrusted spans carrying a matching `principal_id`.
  - The exemption is bound to a new `SecurityContext.principal_id`, never to `source_id`. `source_id` is a descriptive label that is not unique across source types, so an unrelated `mcp_server` span sharing a string with an `mcp_client` one would have ridden out on a collision.
  - Deliberately narrow, and verified so rather than asserted: only the untrusted selection is filtered. Sensitive spans, the remembered canary and the secret scan are all still enforced with an exemption in play, both identities must be truthy so no pair of empty values can match, a different principal is never exempt, and a span the integrator did not attribute is never exempt.
  - Only `Guard.context_mcp_client` accepts a `principal_id`. The server, document, web and internal-sensitive profiles have no such parameter, so tool and server output cannot be attributed to a principal through a profile. Constructing a `SecurityContext` directly can still do it, which is why this is written down as an assumption rather than described as impossible: see **A-AS12**.
  - **The gateway does not use this and cannot yet.** A-AS12 requires an authenticated identity and A-AS11 records that the gateway ships no authentication, so a proxy deployment still blocks answers that restate the question. `docs/gateway.md` says so under "What it is not, yet". An application that wraps the library and brings its own authentication can use it today.
- **`PolicyConfig.destructive_tools`, so a deployment can name its own destructive tools.** The set was reachable only as a `PolicyEngine` constructor argument, and `Guard` builds that engine itself, so a host whose dangerous action was `wire_funds` had no supported way to say so: the built-in set names gmail, calendar, slack, file and shell tools and nothing else. A list now replaces that set rather than extending it, so `[]` is meaningful and a deployment can also declare fewer. Settable from a policy file alongside `untrusted_deny_tools`, because leaving it constructor-only would half-fix the gap for anyone who keeps policy in a file. A bare string is refused rather than iterated, since `destructive_tools="wire_funds"` would otherwise declare eleven single-character tools and leave the real one unguarded. Scope, stated because it is easy to assume otherwise: this gates `enable_destructive`, the authorization requirement, and `require_message_binding="destructive"`. It does not feed the session-risk gate.
- Privacy vault persistence, so a token keeps meaning the same person across a restart. `Guard(privacy=..., vault_store=EncryptedFileVaultStore.from_env(path))` and `guard.persist_vault()`. Needs the new `vault` extra: `pip install 'vordur[vault]'`. The vault remains session state by default and nothing reaches disk on its own: a vault with no store never writes, and a vault with one writes only when asked. Writing on every token would put an fsync on the path of every prompt, and the window that leaves is one the vault already fails closed on.
  - What this buys is continuity, not protection. Nothing crosses to the provider that would not have crossed before. Without a store a restart loses co-reference, so the same person is issued a second token and tokens from before the restart stop resolving; either way an unresolvable token fails the call rather than resolving to the wrong person.
  - **A persisted vault is a different security object from an in-memory one.** In memory it holds plaintext the caller already had; on disk it is a re-identification database mapping every token a provider has seen back to the person behind it, outliving the request and the process. So the store that ships is AES-256-GCM from its first commit and there is no unencrypted alternative behind it: without the extra it refuses to write rather than falling back to plaintext. The key is the caller's, `generate_key()` returns one for a secret manager, and no code path in GuardLLM writes a key anywhere. `from_env` refuses an unset variable rather than generating one and coming up healthy and empty against a file it can no longer read.
  - A file that does not authenticate raises and is never read as an empty vault, because starting empty after a wrong key looks like a fresh session and is not one. Writes are atomic through a same-directory temporary file at mode 0600, so a crash mid-write leaves the previous snapshot rather than half of the new one. `clear()` purges the stored snapshot too: it invalidates every token in the transcript, and leaving the file behind would let the next process resurrect them. The file's *absence* is not authenticated, which is a denial of continuity rather than a disclosure, and is said so in the docs.
  - The snapshot stores entries, source handles, the derived-handle key and the host's seeded values, and rebuilds the payload, issued-body and trigram indexes from the entries on load rather than storing them, because a stored index can disagree with the entries it indexes and the failure that causes is a token resolving to the wrong person. It refuses to load into a vault that has already issued tokens, refuses more entries than `vault_max_entries` since capacity is the forgery bound rather than a memory limit, and refuses an unknown `PIIClass` rather than dropping the entry. Snapshot and entry `repr` count rather than quote.
  - **A snapshot is checked as a whole before any of it is indexed**, because an AEAD proves who wrote a file and not that what it holds is coherent, and `VaultStore` is an interface anyone may implement. Two entries under one codeword body are refused (that snapshot resolved the first person's token to the second), as are a body that is not a canonical codeword, a body that decodes only after error correction, one value under two codewords, a repeated source, and a malformed seeded pair. Every check runs before the first write, so a snapshot that fails one leaves the vault exactly as it was: a partial load is a vault holding some of a session's identities and silently missing the rest, which reads as a working vault.
  - `VaultStore` is a three-method protocol (`load`, `save`, `purge`) and a third long-lived interface: within `VAULT_SNAPSHOT_VERSION`, fields are only ever added. Key rotation, escrow, HA and deletion evidence sit above it without changing it.
- Support bundle: `python -m vordur.support -o bundle.json`, or `GET /support` and `GET /support/<session-id>` on the gateway. Customer-hosted delivery means nobody outside your network can look at a failing system, so when a call is refused and should not have been, the entire evidence base is what an operator can be talked through producing. One file replaces that exchange. It carries the resolved policy with `changed_from_default` naming every setting that is not stock, GuardLLM and Python versions, whether the optional extras (`yaml`, `wasmtime`, `cryptography`) can actually be imported, and the session's decision chain. It never reports "no policy": with no file configured the defaults are in force and are what refused the call, so they are reported as such.
  - What it refuses to carry is the reason it lives in the library rather than in a support runbook. No message content, ever: the chain names stages, tools and verdicts, and the reason strings are written to exclude the values they describe. Environment variables by name and never by value, since a `GUARDLLM_UPSTREAM` can hold a key inside a query string. And the bundle is scanned by the same two passes that guard egress before it is written.
  - A credential the scan can locate is replaced with `[redacted: credential]`. A credential it recognizes but cannot locate exactly means **nothing is written at all**: `UnsafeBundleError`, exit code 2, or `409` from the gateway. Attribution says which characters can be replaced and recognition says a credential is present, so when recognition fires and attribution has nothing to replace, redacting would produce a file that looks cleaned and is not. An earlier version of the check compared label and span counts and let through the case that matters most, one document holding one locatable key and one unlocatable one; any recognition surviving the mask is now a refusal.
- Both long-lived interfaces created for the gateway now carry a version, because a customer-hosted deployment runs a release for years and cannot be forced forward, and neither the policy file nor the Rego input document is ours to change once a customer has written against it. Within a version, settings and fields are only ever **added**; none is removed, renamed, or given a new meaning.
  - Policy files take an optional top-level `version:`. Absent means 1, so every file already written keeps working and no boilerplate is required. The direction that needed guarding is an *old* build reading a *new* file: without the key it would meet settings it does not implement, refuse them under the unknown-key rule, and report a typo, when the truth is that the operator's policy is not being enforced as written. A version this build does not know is refused, and the two directions are distinguished in the message because the remedies are opposite: a newer file needs a newer GuardLLM, a retired version needs the file migrating. `vordur.config.POLICY_FILE_VERSION` and `SUPPORTED_POLICY_FILE_VERSIONS`.
  - The Rego input document carries `input.version`, inside the document rather than beside it, so a policy can branch on it and keep working across an increment instead of failing at the first changed field. `vordur.policy.POLICY_INPUT_VERSION`.
- Rego policy evaluation, in process and with no network: `vordur.policy.RegoPolicy` loads a policy compiled by `opa build -t wasm` and evaluates it through wasmtime in microseconds. Needs the new `rego` extra: `pip install 'guardllm[rego]'`. The `opa` binary is a build-time tool for whoever compiles the policy, never a runtime dependency. Local is the point: the library claims it makes no external API calls, and an HTTP hop to a policy server inside the policy engine would end that, so a central OPA attaches at the gateway instead.
  - The input document is the interface, and `build_input` is its single definition. Everything under `guardllm` is a fact no other policy engine can know: `session_contaminated`, `session_escalated`, `untrusted_sources`, `injection_detected`, `canary_detected`, `binding_valid`. That is what lets a customer write "a session that ingested untrusted content may not move money", which OPA alone cannot express because nothing else computes it.
  - Ordering is enforced by `decide`, strictest wins: GuardLLM's checks run first, **a GuardLLM deny is final and the policy is not consulted at all**, and on an allow Rego may still deny. A policy able to overturn a deny would be a way to configure the enforcement off. Rego only ever narrows.
  - The document is total on purpose. In Rego an undefined reference makes the whole rule body undefined, so a rule reading a field the input lacks does not deny, it fails to fire, and an access rule that fails to fire fails open. Measured on the fixture policy: an absent `user.roles` let `delete_account` through while `roles: []` denied it, so `user.roles` is now always present as a list.
- Session forensics viewer on the gateway: `GET /forensics` lists live sessions and `GET /forensics/<id>` shows one session's decision chain, with the same data as JSON at `GET /sessions` and `GET /sessions/<id>`. Each step names the stage, the tool or source it concerned, the verdict, and the contamination and escalation flags as they stood at that moment, so a refusal several turns after the ingest that caused it is legible as one sequence rather than three unrelated verdicts. That relationship is what a per-request log cannot show. The page is self-contained: no JavaScript, no external assets, renders with no network. It holds no content, only stages, subjects and reasons, and the chain is bounded at 200 steps per session. Ephemeral by design, in memory and lost on restart; retention and search across restarts are a separate concern. Viewing a session never creates one.
- Gateway: an OpenAI-compatible proxy that runs the checks itself, so an application changes only its `base_url` and makes no GuardLLM calls. `docker run -p 8080:8080 -e GUARDLLM_UPSTREAM=... guardllm/gateway`, or `python -m guardllm.gateway`. A `tool` role message is ingested as untrusted content and can contaminate the session; the model's reply is checked on the way back, tool-call arguments through the authorization gate and text through outbound DLP. Because both run against one in-memory session keyed by an `X-GuardLLM-Session` header, the session-risk loop holds across requests. Provenance is taken from the channel (message role, tool name), never the content, so the "nothing inferred from content" rule survives the move into a proxy. The client's `Authorization` header is forwarded verbatim: the gateway never holds an upstream key. Fails closed and loud, emits audit events to stdout, and answers `GET /healthz`. The HTTP shell is standard library only, so the container adds no web framework. Single-instance tier: state is in memory and streaming is not yet inspected incrementally. See `docs/gateway.md`.
- `vordur.config.load_policy(path)` and `parse_policy(text)` build a `PolicyConfig` from YAML, for a deployment that has no Python object to put one in. Needs PyYAML via the new `yaml` extra: `pip install 'guardllm[yaml]'`. The file expresses the two shapes YAML cannot write directly, the tuple-keyed `tool_allowlist` as a plain list of names and `source_gate_overrides` as a list of rows, and enum values as their strings. Only `safe_load` is used, so a policy file can never construct a Python object. The loader refuses rather than guesses: an unknown key is an error with a suggestion, a value of the wrong type is an error (YAML reads `off` as false but `"false"` as a truthy string, so `enable_destructive: "false"` is refused rather than coerced), an absent `tool_allowlist` stays distinct from an empty one because those mean no allowlist and deny-everything respectively, and `directive_patterns` is refused outright since the policy engine does not read it. `PolicyConfig` validates the option strings it owns, so the loader does not restate them. `PrivacyConfig` is not loadable: it holds detector instances a file cannot name.
- `AuditLogger(stream=...)` writes security events to an open text stream, one JSON object per line, alongside or instead of the file backend. `sys.stdout` is the intended argument in a container, where the collector reads the process's output and there is no file worth mounting, rotating or shipping. Both sinks receive the same serialized record, and the stream is flushed per event: Python block-buffers a stream that is not a terminal, and under a collector stdout is always a pipe, so an unflushed event would sit invisible while the process ran and be lost if it died. The default is unchanged and writes nothing new.
- Privacy vault: pseudonymization at the model boundary, with restoration scoped by tool field and by destination. Personal data detected on the way in is replaced with an opaque token before the prompt reaches the provider, and the real value is put back only where policy says it may go. Entirely opt-in: `Guard(..., privacy=PrivacyConfig(...))` or `SecurityPipeline(..., privacy=...)` constructs a vault, and without it nothing in this feature runs and no existing verdict changes. `seed_private_values`, `deidentify`, and `reidentify` raise `ValueError` when no vault was configured, rather than returning something that looks like a result; `prepare_tool_call` instead passes the arguments through with `reason="privacy disabled"`, so a host can call it unconditionally in its dispatch path. Surface: `Guard.seed_private_values`, `.deidentify`, `.reidentify`, `.prepare_tool_call`; `PrivacyConfig`, `PIIClass`, `ClassPolicy`, `Destination`, `PIIFinding`, `Detector`, `DeidentifyResult`, `PreparedCall`; and `SecurityPipeline.vault` for direct access. `ProcessedContent` gains `pii_findings`, `blocked`, `detection_incomplete`, and `inference_used`, all defaulted so existing readers are unaffected.
  - Detection ships two tiers and neither infers. **Declared values** are seeded by the host from a session it has already authenticated, so precision is exact. **Pattern detection** covers structured identifiers deterministically: email, phone, SSN, credit card by Luhn, IBAN, routing number, passport, driver's licence, national identity number, medical record number, and date of birth. A third tier is available through the `Detector` protocol for hosts that want to plug in their own recognizer; registration order cannot remove a finding another detector produced. `PrivacyConfig.classes` defaults to thirteen classes, two of which, `PERSON` and `ADDRESS`, no pattern can find: they are reachable only through seeded declared values or a registered detector, and are in the default set so that a host which does seed them gets them tokenized without extra configuration.
  - Restoration is deny-by-default in both directions. `restore_policy` maps a tool and a field path to the classes restorable there, `destination_policy` maps a destination to the classes it may receive, and a field or destination with no rule restores nothing. `prepare_tool_call` resolves tokens before the host builds its authorization event and binding, because both bind exact bytes and a scope authorized over a token fails against the restored value.
  - Fails closed throughout. A token that cannot be resolved, a token whose framing the model damaged, an unresolvable count past `max_unresolvable`, a vault at `vault_max_entries`, or an argument tree past `max_arg_depth` or `max_arg_nodes` all refuse the call rather than dispatching a partially resolved one. Tokens carry a Reed-Solomon check (`token_codec`) that corrects a single mangled symbol and refuses two, so an off-by-one transcription by the model is recovered rather than silently misresolved.

### Changed
- **The project is now Vörður, the Icelandic word for guardian.** Two spellings, and which one applies is mechanical rather than a matter of taste: Vörður is the name and appears in headings and prose, `vordur` is the identifier and appears only in code font. The identifier is introduced once per document, in the first sentence naming the package. `tests/test_naming_rule.py` enforces this, including that the unaccented "Vordur" never appears in prose, since it is neither the word nor the identifier.
  - **Breaking: the import path.** `import guardllm` becomes `import vordur`. Every module moves with it, `guardllm.security.types` to `vordur.security.types` and so on. The public surface is otherwise unchanged: `Guard` and every method on it keep their names.
  - **Breaking: the session header.** The gateway's `X-GuardLLM-Session` becomes `X-Vordur-Session`. A header field name is a protocol token and must be ASCII, so this one takes the identifier spelling rather than the name. A client sending the old header starts a new session rather than joining its existing one.
  - **Breaking: the gateway error type.** The `type` field in the OpenAI-compatible error envelope changes from `guardllm_gateway` to `vordur_gateway`.
  - **Environment variables are renamed and the old names still work.** `VORDUR_*` is canonical. `GUARDLLM_*` is still read, once, with a `DeprecationWarning` naming the replacement, so an upgrade cannot silently drop a working configuration: a `GUARDLLM_POLICY` that stopped being read would leave the gateway starting with no policy, which looks exactly like a healthy start. There is precedent for this in `EPISODIC_CANARY_SECRET`, which predates the project's earlier name and is still honoured. The diagnostic bundle reports set variables under both prefixes.
  - **The generated demo pages are renamed**, `guardllm_demos.html` to `vordur_demos.html` and so on for all twelve.
  - **The published site moves** from `/guardllm` to `/vordur`.
- **Not renamed, deliberately.** Strategy keys inside frozen benchmark artifacts stay `guardllm` and `guardllm_surface`: `benchmarks/published/surface_controls.json`, `benchmarks/results/comparison.json` and both verification packets are records of runs that happened under that name, and the benchmark code that reads them keeps matching variable names so the code does not disagree with its own data. Changelog entries below this one likewise describe what shipped as GuardLLM and are left alone.
- The API reference states the session contract: one `Guard` per session and per principal, driven sequentially, with `principal_trust` fixed at construction and checked on every call, which raises `ValueError("principal_trust mismatch: ...")` and was documented nowhere. It also documents `context_internal_sensitive`, `principal_id`, the `principal_trust` builder keyword, the 300-second authorization TTL, the missing-confirmation-handler reason string and audit event, `PolicyConfig.destructive_tools`, and every audit event type. `docs/api_spec.md` is declared authoritative over `docs/api.md`, and tests now pin the reference to the code.
- `Guard` refuses an `audit_logger` without a callable `log` at construction with `TypeError`. It was accepted and then ignored on every event, so the trail a deployment configured never existed and nothing said so.
- The date-of-birth validator's ceiling is the current year, read at call time, rather than the literal `2025` it was written with.
- The package root exports every type a `Guard` method accepts or returns: the privacy types (`PrivacyConfig`, `PIIClass`, `ClassPolicy`, `Destination`, `PIIFinding`, `Detector`, `DetectedSpan`, `DeidentifyResult`, `ReidentifyResult`, `PreparedCall`) and `ConfirmationHandler`, `AuditLogger`, `SanitizationResult`, `RateLimitResult`, `ExtractionPolicy`. Importing them from `vordur.security.types` still works.
- The `Guard` docstring states the session contract: one Guard per session and principal, `principal_trust` fixed at construction, sequential use.
- A missing confirmation handler is now reported as a configuration failure rather than as a user decision. `guard_tool_call(..., require_confirmation=True)` against a `SecurityContext` with no `confirmation_handler` previously denied with `reason="User denied confirmation"` and audited `user_confirmed=False`, although no user was consulted: the reason read like a working confirmation flow that an operator declined, so a missing handler failed quietly rather than obviously, and the audit trail asserted a decision nobody made. The call still denies. It now returns `reason="Confirmation unavailable: no confirmation handler configured"` and emits an `action_gate_unavailable` audit event with `user_confirmed=None`. `reason="User denied confirmation"` and `user_confirmed=False` are preserved for the case a handler actually returned False. **Callers matching on the reason string for the missing-handler case need to update.**
- The L6 rapid-burst anomaly now counts the action being checked, not only the actions already completed in the window. `burst_threshold=3` previously required three completed actions before flagging anything, so the signal first appeared on the *fourth* proposal and a burst of exactly three actions inside `burst_window_seconds` produced no anomaly at all. The third action in the window is now flagged, and the reported count names that action's own position (`Rapid burst: 3 actions in 10s` on the third send rather than the fourth). The burst signal is advisory and never blocks, so this changes which calls carry an anomaly, not which calls are permitted. The hourly cap is unchanged and still counts only completed actions, because it governs quota and must reflect what actually happened. Hosts that treat `anomalies` as an alerting trigger will see burst alerts one action earlier. Documented in `docs/policy_tuning.md`.
- Threat model (`docs/threat_model.md`) rescoped to match the implementation: request binding is described as an intra-process consistency check (recomputed argument hash, message-hash match, TTL) rather than a cryptographic binding, and authorization-event origin authenticity is stated as a host obligation (the library validates event contents, not origin). `PolicyConfig.directive_patterns` is documented as reserved and not yet wired.

### Fixed
- **A tool gate that let a call through under session risk named the wrong cause.** With a contaminated session and `contaminated_tool_policy="allow"`, the result read `Non-destructive tool, implicit allow`, which attributes the outcome to the tool's classification when classification did not participate: under `deny` a declared tool and an undeclared one are refused with the identical string, and under `allow` both pass. Two independent reviewers read that string as evidence that declaring the tool would have changed the verdict. An allow that ran with a session-risk signal active now appends the signal and the setting that decided, for example `[session risk present: session contaminated=allow]`. A clean session is unchanged.
- **An enabled PII class with no detector behind it reported `clean`.** `DEFAULT_TOKENIZE_CLASSES` includes `PERSON` and `ADDRESS`, and the library deliberately declines to infer either from free text, so a host that enabled the vault and changed nothing had asked for name coverage it did not have. De-identifying `Marguerite Vasquez, m.vasquez@clinic.example, 44 Sycamore Lane` tokenized the address and returned the name and the street in the clear with `reason='clean'`, `warnings=[]` and `detection_incomplete=False`. The behaviour is intended; the silence was not. `detection_incomplete` could not carry it either, because that flag means a detector which ran could not finish and a detector that was never registered reports nothing. The result now warns, naming the classes nothing scanned for. Cleared by seeding a value of that class, registering a `Detector` for it, or narrowing `PrivacyConfig.classes`; `CREDENTIAL` is excluded because it is covered by `credential_spans` rather than the structural table.
- **Benchmark provenance and split hygiene.** Four defects in how the benchmarks identify and partition the data behind their numbers. None changes what GuardLLM enforces; all four change whether a published figure can be trusted to describe the data it claims.
  - **A checkpoint could not tell that the cases had changed.** It recorded summary counts and failed ids, so replacing a passing case with an unrelated passing case left every number identical and raised nothing: the baseline vouched for a corpus nobody could identify. Checkpoints now carry a content fingerprint over the cases in the suites they cover, so a swapped case, an edited input, and a flipped expectation each invalidate it. Scoped to the checkpoint's own suites, so `--allow-extra-suites` still works and a developer's untracked upstream corpora do not disturb it. A checkpoint written before this reports itself as unverified rather than passing silently. The committed baseline was regenerated; its summary and failed ids are byte-identical to the previous one, so only the fingerprint is new.
  - **Cached provider results were reused across unrelated datasets.** The gate was the injection scope and the record *count*, so two entirely different corpora of the same size matched and a previous run's vendor summaries, latencies and per-record predictions were copied into a run that never evaluated them: one comparison table could mix current GuardLLM results with vendor results measured on other content. Reuse now also requires the same record content, and a run that cannot say what it evaluated is not reused at all.
  - **Duplicate texts crossed the ROC/PR dev and test split.** The split stratified by suite and label but shuffled individual records, so on the canonical corpus 61 distinct texts appeared on both sides, 417 cross-split record pairs. Thresholds are selected on dev and then reported as frozen test results, so a text seen while selecting could be counted again as held out, inflating the operating points. Records sharing a text now move as one unit, and the clusters are global rather than per stratum, because the first attempt still leaked one text that lived in two suites. Measured after: 0 texts on both sides, split still deterministic from its seed and still a complete, disjoint partition. **This changes the ROC/PR operating points**, which is the point of the fix; the untuned headline F1 is computed on all records and is unaffected.
  - `meets_budget_dev` was computed from the test point for non-tunable methods, so a field labelled dev reported the test result. It now comes from the dev split, and the dev point is serialized alongside the test one.
- **A secret cut across two tool-argument fields passed both halves.** The argument scan checked each field alone, so `{"left": "AKIA", "right": "IOSFODNN7EXAMPLE"}` was allowed while the same twenty characters in one field were blocked. The same split worked on a canary and on a passage copied from ingested content. What leaves the boundary is the whole call, so the call's string values are now joined, in traversal order and with field names excluded, and checked as one payload after each field is checked on its own. Both the gateway and `prepare_tool_call` do it. Verified across two fields, three fields, and values nested in maps and lists; ordinary calls are unaffected.
  - **This narrows the gap rather than closing it, and the limits are pinned by a test rather than left to be assumed.** Values join in traversal order, so a caller that controls field ordering can place the halves so no ordering produced here makes them adjacent, and covering every permutation is factorial. No per-call check reaches a secret sent one half per request either; that needs cross-request accumulation, which is a different mechanism.
- **Evicting a session silently relaxed it, and any client could force that.** Sessions are held under an LRU and a TTL, and both rebuilt an evicted id as a clean `Guard`. The module reasoned that a rebuild is stricter; that is wrong in exactly one direction, because contamination and escalation only ever *tighten* policy, so a clean rebuild is looser than the session it replaced. Reproduced: a contaminated session denied `wire_funds`, an unrelated client filled the LRU with one id of its own, and the same session id then allowed `wire_funds` again. The TTL path had the same effect without an attacker.
  - Eviction now records the id of any session that was contaminated or escalated, two booleans per id, and a returning id is rebuilt with those flags. `Guard.carry_session_risk` is the new, deliberately monotonic entry point: it can raise these flags and never lower them, because a setter that could clear them would be a way to launder a contaminated session back to clean. A never-seen id is still a clean session, a clean eviction records nothing, and the ledger is bounded like everything else in the store.
  - What eviction still costs is the DLP buffers and provenance spans, which two booleans cannot reconstruct: copying from content ingested before an eviction is no longer detected. The tool gate, which is what the flags drive, is. `docs/gateway.md` and the module docstring now say this rather than the reasoning that turned out to be wrong.
- **The 50,000-character overlap cap was a prefix-only check, and a bypass in both directions.** Outbound content was truncated to the cap before the verbatim-overlap and provenance comparisons, so padding a payload with 50,001 characters moved the copied passage out of the compared prefix and turned a block into `clean`. Ingested content was truncated the same way, so a passage copied out of the tail of a 60,000-character document was never compared either. Both reproduced, at several sizes and positions.
  - The comparisons now scan the whole of both sides in overlapping windows, with the lap far above any configured threshold so a match straddling a seam is still found. Content beyond what will be scanned is **refused** rather than truncated, because reporting clean on bytes that were never read is the defect. Ingested documents are buffered as windows instead of a truncated head, so a large document occupies several buffer slots rather than silently losing its tail; the per-entry and total memory bounds are unchanged.
  - The expensive substring check is now gated on a shared gram the length of the threshold, which is exact: a common substring of length L contains a gram of length L, so no shared gram proves no blocking overlap. The previous 5-gram gate is a far weaker test that ordinary prose passes constantly. Together with building each window's gram sets once per batch instead of once per reference, the worst case the buffer already allowed (fifty entries at the per-entry cap) went from **383 seconds to 7**, and peak memory from 445MB to 62MB. One visible consequence: a longest-common-substring length *below* the threshold is now reported as 0 rather than measured, since nothing decides on a sub-threshold value. This changes one demo fixture's `echo_lcs` metadata from 6 to 0 and no verdict anywhere.
- The forensics index escaped session ids for HTML but did not encode them for the URL path, so an id containing `?` or `#` produced a link to a *different* session: everything after the `?` became a query string and after the `#` a fragment the server never receives. The path component is now percent-encoded, which round-trips through the `unquote` the server already performs. The store now also rejects those characters, so this is defence in depth rather than a live exploit.
- **Both CBX generators could not regenerate their pinned datasets from a clean checkout.** Each shallow-cloned the upstream default branch and then asserted `HEAD` equalled a pinned commit, without ever fetching or checking that commit out, so the assertion failed as soon as upstream moved: `gen_cbx1000.py` and `gen_cbx1200.py` both aborted with `HEAD=089ed468... expected=462c88dd...`. They now fetch the pinned sha directly and check it out, which is exact and cheaper than cloning a branch and hoping. Verified against the repository that was failing: it lands on `462c88dd` and stays there on a warm cache.
- **The gateway's upstream timeout was not a deadline.** `urllib`'s `timeout` is a socket inactivity timeout that resets on every byte, so an upstream delivering a byte often enough held the connection indefinitely: a 124-byte response drip-fed one byte per second completed in 123.9 seconds under a 120-second timeout. `ThreadingHTTPServer` gives each request a thread, so that is a worker held per connection, in the component every request passes through. The response is now read in chunks with a total wall-clock deadline checked between them, using `read1` so a slow sender returns what it has rather than blocking for a full chunk. Completes the byte cap added earlier, which bounded size but not time.
- **Client-supplied session ids were unbounded.** They are unauthenticated, and each becomes a dictionary key, a response header, and a row in the forensics index: a 60,000-character id was accepted, retained even after the upstream call failed, and echoed back in the error response, and 200 of them held 12.7MB against a ceiling of 10,000 sessions. Ids are now limited to 128 characters of `[A-Za-z0-9._~-]`, which covers hex, UUIDs, and base64url, and a malformed one is a `400` refused before anything is stored. Refused rather than truncated or hashed, because a silently altered id sends the client's next request to a different session than the one it believes it is continuing. An absent id still yields a fresh session, unchanged.
- **Expiry failed open on non-finite and future timestamps, defeating replay protection.** Both TTL checks were a single `elapsed > ttl` comparison, which is False in three cases that all mean "never expires": `NaN` anywhere (every comparison against it is False, and JSON and YAML can both carry it), an infinite timestamp (`elapsed` becomes `-inf`), and a timestamp far enough in the future (`elapsed` stays negative for as long as the caller chose). Reproduced through the real gates: an authorization a million seconds old was correctly refused while `NaN`, `inf`, and a far-future timestamp all returned "Authorization verified", and a binding with a `NaN` TTL created 1e9 seconds ago verified clean. Replay protection is the control these TTLs implement, so this was the defeat of the mechanism rather than a cosmetic issue. Both now use `types.expiry_reason`, an explicit accept-range that refuses anything not finite and anything outside `[-skew, ttl]`, with 60 seconds of clock skew allowed because an authorization event may be minted on another host.
- **A credential used as a tool-argument name was copied verbatim into validation errors and the audit stream.** Argument names arrive from a model-proposed tool call and the errors quoting them travel further than the call does: into the audit record and out through the sanitized error path, while the outbound DLP that catches a credential in a *value* never inspects a *key*. Reproduced with a GitHub token as the argument name; the whole token appeared in both. Names are now echoed only if they both look like a plausible parameter identifier and carry nothing the credential scanner recognizes, and anything else is replaced by a stable digest reference that still lets an operator correlate repeated reports. Both gates are needed: a GitHub token is exactly 40 characters of identifier-legal text and an AWS key ID is 20, so no length bound alone separates them from real names.
- The three dataset-hash implementations disagreed. The builder serialized with compact separators and `ensure_ascii=False`; the two evaluators used default separators and `ensure_ascii=True`. An identical case list therefore hashed two ways, so `METADATA.json`'s value could never be compared with `comparison.json`'s and neither artifact could confirm the other had evaluated the same data, which is the only thing the field is for. All three now delegate to one implementation in `_bootstrap`, the module they already share, so they cannot drift again. Content sensitivity and key-order independence are covered by a test asserting all three agree.
- The overlap-threshold validation accepted non-finite values, which is the one out-of-range value that is itself the disabling failure the check exists to catch: every `overlap >= NaN` is false, so a threshold of `NaN` silently never blocks, and YAML spells it `.nan` so a policy file could reach it. Non-finite n-gram thresholds are now refused, and a test covers the YAML path. An incomplete fix, corrected before release.
- The five overlap thresholds on `PolicyConfig` were accepted without validation, and one class of value silently disabled enforcement rather than tightening it: each LCS minimum is computed only when the spans share a 5-gram, so `provenance_verbatim_lcs_min=3` meant a 3-character verbatim overlap never shared a 5-gram, the LCS was skipped, and the block never fired. `PolicyConfig` now refuses an LCS threshold below the 5-gram gate and a non-numeric threshold at construction. The n-gram thresholds are not range-checked: unlike the LCS minimum an out-of-range value there does not read as stricter while being off (0.0 always runs the LCS, and a value above 1.0 is the supported way to disable the gate), so only a non-number is refused.
- Two identifier evasions crossed `deidentify` to the model with no finding, both the same shape: an ASCII pattern against a non-ASCII identifier. An email split by a zero-width space (`jane<ZWSP>@example.com`) broke the email pattern, and a card number in Arabic-Indic or other Unicode decimal digits was `isdigit()`-true but not `[0-9]`, so it never matched the credit-card pattern (and the Luhn validator's `ord(ch)-48` was ASCII-only regardless). The structural detectors now run on a normalized copy, Unicode digits folded to ASCII and format characters (zero-width, bidi, tag-plane, soft hyphen) dropped, with every span mapped back to original offsets so substitution still cuts the exact original characters, the hidden one included. Verified at every split position and across four Unicode digit sets. The credential scanner keeps running on the raw text, because it already separates a secret split by an invisible from ordinary prose split by one, and feeding it the stripped copy merged prose into a false high-entropy hit.
- The gateway followed HTTP redirects from the upstream and resent the client's `Authorization` header to the new location, so a `302` from the model API to an unrelated origin handed that origin a bearer token the gateway forwards but does not own. Reproduced against two loopback servers: the token reached the second origin. `urllib` follows redirects by default; the gateway now refuses every `3xx` from the upstream, because a completions endpoint has no legitimate reason to redirect and the narrow rule is the one that cannot leak. This also makes `docs/gateway.md`'s "the gateway never holds an upstream key" true again.
- The gateway read the upstream response body with an unbounded `read()`, so a compromised or malfunctioning model API could allocate arbitrary gateway memory before any inspection ran. The read is now capped at 8MB, the same bound already applied to the inbound request, and an oversized body is surfaced as a `502` rather than buffered.
- **The gateway's new tool-argument check spent the quota of the call it was checking.** `check_outbound` records an outbound action against the L6 rate limiter every time it is called, and the argument scan looped it over every string leaf, so one stock `send_email` charged a single send six times. The second tool call of any session was refused with "Hourly limit exceeded (10/10)" and the session stayed refused for the window. The leaf loop now uses the non-recording variant, which `prepare_tool_call` has always used for the same reason; that variant is exposed as `Guard.check_outbound_content`. Escalation still propagates from an argument block, and exfiltration through an argument is still refused. Introduced and fixed before any release.
- **`rate_limits` and `argument_limits` were enforced but not validated.** `rate_limit_overrides` beside them was checked against the valid key set and these were not, so `emails_per_hr: 2` merged cleanly and left the default of ten in force with nothing reporting that the setting had not taken, which is the failure enforcing the field was meant to end. Wrong types were worse: `max_chars: "50"` raised a `TypeError` comparing int to str from inside whichever tool call carried that argument, and a `pattern` that did not compile raised from `re`, both as unhandled errors at dispatch rather than at policy load. `PolicyConfig` now refuses unknown keys, wrong types, and uncompilable patterns at construction.
- `Guard(vault_store=...)` without `privacy=` built no vault, stored nothing, and raised nothing, then reported "constructed without privacy" at the first `persist_vault` call, which a host may not make until shutdown. It now raises at construction: persistence configured but never happening is the failure `persist_vault` refuses by name.
- A vault snapshot with two distinct sources under one handle loaded cleanly, presenting two unrelated documents to the model as one source. That is the collision `_SOURCE_HANDLE_MAX` exists to make improbable, and the inverse of the duplicate-source check already beside it. Now refused.
- `EncryptedFileVaultStore.load` let a raw `OSError` escape, contradicting the `VaultStore.load` contract of None-or-`VaultStoreError`: a vault file with the wrong ownership surfaced as a bare `PermissionError` out of the `Guard` constructor. It is now wrapped, and the read-then-catch also closes a window where a concurrent `purge()` turned the read into `FileNotFoundError` where the contract promises None.
- A Rego bundle carrying a `data.json` outside its root is now refused rather than silently ignored. `opa build` merges every data file into one root document keyed by directory, so a bundle it produced never has one, but the bundle format permits them and other tooling can emit them; reading only the root would drop that data and a rule reading it would fail open. Refused rather than merged, because guessing at a layout `opa` did not write is how the two come to disagree.
- **A Rego policy could fail open in two ways, silently.** Both are the same shape: in Rego an undefined reference makes the enclosing rule body undefined, so a `deny` rule that meets one does not deny, it fails to fire, and the call is allowed. Measured against `opa eval` on the same bundle and input, where OPA returned two deny messages and GuardLLM returned "no policy objection".
  - **A bundle's `data.json` was never loaded.** The WASM ABI takes the data document as a caller-supplied argument and nothing is compiled into the module, so passing `{}` left every `data.` reference undefined. A comment claimed a bundle's own data still applied; it did not. The bundle's data document is now parsed and passed, and a test asserts GuardLLM's verdict equals `opa eval`'s on the same input.
  - **Builtins OPA does not compile into the module were answered with 0**, which reads as undefined. They are now **refused at load**, naming them, rather than stubbed at evaluation. `sprintf` is the common one, because it is how a deny message interpolates what it objected to; a literal message needs no builtin, and the fixture policy in this repository needs none at all. A loud refusal once, before the policy is trusted with a decision, beats a policy that evaluates and permits.
- **The Rego evaluator leaked memory on every call.** The WASM heap pointer was read but never wound back, so each evaluation kept its input and result allocations: about 2.2 KB per call, 55 MB after 26,000, never reclaimed. A gateway evaluates a policy on every tool call and runs for weeks, so this was an availability failure in the security layer. The heap is now reset to a mark taken after the data document is parsed, so the data survives and the per-call allocations do not. Measured flat across 30,000 evaluations, verdicts unchanged.
- **The gateway did not inspect tool-call argument content.** `check_tool_call` gates the *action* (policy, rate limit, binding) and does not read the payload; in library mode that split is A-AS9, a host obligation, because only the host knows which arguments carry content. `docs/threat_model.md` said the proxy removes A-AS9 as something the application can forget, and the proxy did not close it. Reproduced: a credential lifted out of an ingested tool result and placed in a `send_email` body was **allowed** as a tool argument while the same bytes as assistant text were refused. Every string leaf of a tool call's arguments, keys included, now goes through outbound DLP and provenance before the call is allowed, exactly as `prepare_tool_call` already did.
- **`PolicyConfig.rate_limits` and `PolicyConfig.argument_limits` were accepted, documented, and read by nothing.** `emails_per_hour: 0` still allowed ten, and `query.max_chars: 1` still accepted a two-character query, with no error anywhere. Both are now enforced at the point that owns them: `rate_limits` merges over the defaults as this context's base, under any `rate_limit_overrides` for the principal's trust level; `argument_limits` merges over the defaults by argument name, so a partial override keeps that argument's sibling settings and a name the defaults do not know is added. Neither merge mutates the module-level defaults. A security setting that is accepted and not enforced is worse than one that is refused.
- **The gateway did not serialize a session's requests.** A `Guard` mutates session state in place with no internal synchronization and `docs/security.md` states the contract: one pipeline per session, driven sequentially, and a host that may drive one concurrently holds a lock. `ThreadingHTTPServer` makes the gateway that host, and two requests carrying the same `X-GuardLLM-Session` could interleave a contamination write with an egress read. Each session now carries a lock, held across both inspections *and* the upstream round trip: releasing it over the network would let a second request's ingest land between the first's ingest and its egress check, which is the session-risk loop the gateway exists to hold. Different sessions never contend.
- **Session TTL was not enforced on the diagnostic reads.** Expiry ran only on the chat path, so an idle gateway kept an expired session listed and its decision chain readable indefinitely: a retention window with no upper bound, in the one surface built for someone to read a session back. `chain()` and `listing()` now sweep.
- `GatewayConfig.tool_result_trust` claimed in its own comment that a deployment piping untrusted text into user turns "declares that here", and `docs/gateway.md` said the same about configuration generally. Neither was true of any setting that exists: the field sets the trust level of the one channel the gateway ingests, and adding channels needs a role-to-provenance map there is no design for yet. Both now say what is actually the case.
- A confirmation the user denies no longer consumes L6 rate-limit quota. The guard flow previously recorded the tool action against the rate limiter before the confirmation ran, so a denied confirmation still burned a per-session slot. The record is now deferred until the call has cleared confirmation and G6 commitment verification.
- Confirmed tool calls can no longer exceed the rate limit under concurrency. The deferral above left the rate-limit check before the confirmation `await` and the record after it, so two concurrent confirmed calls could both pass a near-full limit before either recorded. The finalize step now re-checks and records under the rate limiter's lock (`RateLimiter.check_and_record`), so at most `limit` confirmed calls are admitted under both asyncio concurrency and multiple OS threads.

### Security
- **Inbound content is bounded, and the bound refuses rather than truncates.** `process_inbound` returns `ProcessedContent(blocked=True)` with the content withheld for input over `MAX_INBOUND_CHARS` (1,000,000 characters), and for input that would push the session past what its provenance tracker retains (`MAX_PROVENANCE_SPANS` 10,000 spans, `MAX_PROVENANCE_CHARS` 2,000,000 normalized characters). Provenance spans were kept without limit and renormalized on every egress check, so each `check_outbound` cost the session's whole ingest history over again: measured at 3.3 seconds per check after 1,600 documents. Spans are now normalized and windowed once at ingest, and the tracker never evicts, because evicting the oldest span would let a flood of junk flush a sensitive span out of the no-copy check. A session at the budget is a boundary the host has to `reset()` deliberately.
- **Two scans over untrusted input were quadratic.** The email detector's greedy local part restarted inside every long run of local-part characters, so a base64 blob cost the square of its length (1.0s at 40,000 characters); a lookbehind now starts each run once, which changes no match. The sanitizer's hidden-class scan walked to the closing brace once per `.class {` opener, so a `<style>` block with many openers and no close cost the product; it is now one pass per rule block. Both are pinned by timing tests.
- **G6 commitments are keyed by tool and arguments, and verify once.** One slot per tool meant two confirmations of the same tool in flight overwrote each other, and the first to verify was refused as "args changed" against the second's arguments: fail-closed, but a spurious denial of a call the user did confirm. Pending commitments are bounded per tool.
- **The privacy vault's scans read its indexes under the issuance lock.** `issue_batch` grows the payload and trigram indexes under `_lock`; the damaged-token scan and the diagnostic scrub iterated them without it, so a scan running while another thread issued a token could raise mid-iteration.
- **Argument patterns match the whole value.** The declared patterns end in `$`, which also matches before a trailing newline, so `thread_handle="abc\n"` passed a pattern written to admit `abc`. Validation uses `fullmatch`.
- G6 action-gate commitment now binds the exact argument bytes. `canonicalize_args` previously normalized whitespace, so a confirmed `{"cmd": "a\nb"}` and an executed `{"cmd": "a b"}` verified against the same commitment; whitespace-sensitive payloads (shell commands, prompts, regexes, file bodies) could be mutated after confirmation without tripping G6. Verification now compares exact canonical JSON.
- `SecurityContext.mode` is validated in `__post_init__`. It was documented as `"client"` or `"server"` but never checked, and the policy engine treats only exact `"server"` as server mode. A typo such as `mode="sever"` with `server_default_deny=True` silently fell through to the client implicit-allow path and admitted a non-destructive tool. Any mode outside `{"client", "server"}` now raises `ValueError`.
- `PrivacyVault.reidentify(..., allowed_classes=...)` now intersects with `destination_policy` instead of replacing it. It read as a per-call restriction and behaved as a per-call bypass: a destination entitled to `EMAIL` alone restored a full SSN when the caller passed `allowed_classes={PIIClass.SSN}`, so any caller who could choose the destination could choose the classes too, which is the whole of `destination_policy` undone by a keyword argument. Narrowing still narrows; a class the destination does not permit is now withheld however the argument is written.
- `class_policy` can no longer weaken a mandatory-deny class. It was consulted before `DEFAULT_DENY_CLASSES`, so `class_policy={PIIClass.CREDENTIAL: ClassPolicy.ALLOW}` won outright and a recognized OpenAI key crossed to the model provider unchanged. `PrivacyConfig` now raises `ValueError` on such a config rather than ignoring the entry silently, and `policy_for` checks the mandatory-deny set first so a mapping mutated after construction cannot reach the boundary either. **A config that set this raises at construction; it never did what it appeared to do.**
- An alphabet run reports as its own finding, `Alphabet run (ambiguous: a character table or a secret)`, rather than as a generic high-entropy token, and `PrivacyConfig.ambiguous_alphabet_policy` decides what the vault does with one. The RFC 4648 Base32 alphabet in order is also a valid TOTP shared secret, so nothing that inspects the value can separate a character table from a credential, and both automatic answers are wrong: preserving the run returns a possible credential in plaintext, and rewriting it destroys the tables that are the commoner case. `"redact"` (default) replaces the line carrying it, exactly as the ingress path already does for credential material whose extent it could not recover; `"deny"` refuses the content; `"allow"` keeps it, and is the only setting under which such a value can reach a model provider. `check_outbound` reports the run under every setting. `is_ambiguous_finding` is the predicate a caller uses rather than matching the label string.
- A credential that is also an alphabet chart is no longer erased by the monotonic-run suppression. `_monotonic` was consulted by both the span pass and the label pass, which made it the one rule in the module able to remove a credential entirely rather than move it from a span to a label. `234567ABCDEFGHIJKLMNOPQRSTUVWXYZ` is the RFC 4648 Base32 alphabet and also an ordinary TOTP shared secret, and all 32 characters left `check_outbound` with `reason="clean"`. The label pass no longer asks. The span pass still does, so a document holding a character table is never rewritten: over 153 standard library files the spans and the characters they cover are unchanged at 37 and 3,157, and the entire cost is three more files drawing a `High-entropy token` label.
- Outbound credential scanning is restructured into two passes that answer different questions, and this changes verdicts for every deployment, not only those using the privacy vault. Attribution asks which characters can be replaced faithfully and is bounded everywhere, because a span that reaches too far corrupts the document it was protecting. Recognition asks whether a credential is present at all and is bounded nowhere. Every bound in the first pass is a number an attacker can exceed on purpose, and each of them was: 65 separators, 33 shell line continuations, and adjacent empty shell quotes each made a whole credential family disappear while `/bin/sh` still reconstructed the key. A value pushed past a bound now moves from an exact span to a label with no span, so the caller refuses the content rather than releasing it. **Content that previously passed `check_outbound` may now be blocked.**
- A credential split across whitespace, punctuation, quotes, or line continuations is reassembled and replaced exactly, rather than being missed or causing the whole document to be withheld. Compatibility and confusable forms are folded first, so a key rewritten in full-width or mathematical characters is read as the key it is, and invisible characters inside a value no longer end it.
- Credential grammars added for formats that previously registered only as a generic high-entropy token, or not at all: GitHub fine-grained (`github_pat_`) and user-to-server (`ghu_`) tokens, GitLab personal access tokens (`glpat-`), Hugging Face tokens (`hf_`), Stripe secret, restricted, and webhook keys (`sk_live_`, `rk_live_`, `whsec_`), and npm access tokens (`npm_`). A leaked Stripe key was previously reported as an OpenAI API key, because `sk_live_` compacts to a string the `sk` anchor claims; the specific grammar now names it first. npm's legacy registry token is 32 to 40 hex characters with no prefix and was invisible to both passes, since 32 hex characters decode to 16 bytes whose Shannon entropy is capped at 4.0 bits per byte against a 4.5 threshold; it is now found by its `_authToken` config key instead, with the span covering the value only so the line still parses.

## [2.0.0] - 2026-07-10

This release completes the session-risk feedback mechanism designed in the "metadata circulation in the LLM systems loop" work: egress DLP verdicts now persist as session state and gate subsequent tool execution. The `escalated_tool_policy` default of `require_auth` is a behavior-changing default for any deployment that hits the DLP-block-then-tool-call sequence, so this is a major version bump.

### Added
- Egress feedback escalation: the backward-propagating complement of `_context_contaminated`. A DLP hard block at egress (`check_outbound`) now sets a monotonic, session-scoped escalation flag, and subsequent tool calls are gated by the new `PolicyConfig.escalated_tool_policy` (`"allow"` | `"require_auth"` | `"deny"`, default `"require_auth"`). Contamination and escalation are independent signals; when both fire the strictest policy wins, and the denial reason names each contributing trigger with its policy (e.g. `session contaminated=deny; egress escalated=require_auth`). Exposed via a read-only `SecurityPipeline.session_escalated` property. Cleared only by `reset()`, which hosts must call only at genuine session boundaries. See "Session Risk Signals" in `docs/security.md`.
- Benchmark kind `egress_feedback_escalation` covering the mechanism (require_auth default, deny/allow options, strictest-wins vs contamination, monotonicity, and reset clearing).

## [1.2.0] - 2026-07-09

### Security
- Injection detection now strips zero-width, bidi, and tag characters before scanning, so a trigger word split by an invisible character (e.g. U+200B) no longer evades detection.
- Outbound secret scanning now inspects invisible-stripped and whitespace-removed forms, so a key split by a space or zero-width character is still caught. The high-entropy scan gained a length-aware threshold that closes a dead zone for 20-22 character tokens, and covers the whitespace-removed form (gated to digit-bearing tokens to avoid flagging natural language).

- The policy engine now binds client-mode authorizations to the current user message: a mismatching message hash is denied as replay.

Legitimate single-script international text (accented Latin, Cyrillic, en-dashes) is preserved. This also makes the benchmark deterministic across platforms and regardless of whether `confusables` is installed, resolving the cross-platform `upstream_mcpbench` discrepancy noted in the 1.1.0 checkpoint entry.

- Modernized typing across the security package: PEP 585 builtin generics, PEP 604 unions, dropped legacy `typing.Dict`/`List`/`Optional` aliases. Source-level change only; the package already used `from __future__ import annotations`.
- Applied ruff format across the tree for consistent style.
- Regenerated `benchmarks/checkpoints/official-baseline.json` against CI's actual run output (Ubuntu, Python 3.10 through 3.13). The prior checkpoint (captured Feb 22 2026) predated the `error_sanitize_suite` and `tool_gate_contamination_style` suites, the growth of `mcp_protocol_abuse_style` from 5 to 8 cases, and the auth-scope fix in this release. The non-redistributable `upstream_wainjectbench` suite remains gitignored and is excluded from the checkpoint. The 7 expected failures are upstream data bugs (6 in mcpbench, 1 in jailbreakbench) where `expect_contains` is literally not present in `input` due to whitespace differences. Local macOS runs see ~30 additional `upstream_mcpbench` failures on cases containing Polish, French, em-dash, and CJK characters due to platform unicodedata differences with TR39 normalization; those are not regressions and the gate uses CI as the source of truth. New baseline: 7108 cases / 7101 pass / 7 fail (99.9%).
